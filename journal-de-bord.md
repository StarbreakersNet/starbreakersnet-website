## Choix d'écriture du plan (session 1)

- « Fork natif en typescript (comme le projet starbreakers) » interprété comme : le Bonjourr est réécrit nativement dans CE projet (Vue 3 + TypeScript + Vite, mêmes conventions que starbreakers), et non comme un import du dépôt vanilla-TS victrme/Bonjourr ni une iframe. C'est la lecture cohérente avec « comme le projet starbreakers » et avec les deux captures (intégrations directes dans l'app : en-tête « ← Accueil », horloge UserMenu, même châssis).
- Le bouton Bonjourr (bouton_bonjourr.png) est un item du menu existant (src/models/MenuItem.ts) : libellé « Bonjourr », icône maison pleine (fas home), couleur menthe/vert d'eau, et il est en PREMIÈRE position. Sur la capture l'ordre est Bonjourr, Discord, GitLab, Le Zap ; l'ordre actuel du code est GitLab, Discord, Le Zap → je réordonne pour coller à la capture (GitLab passe après Discord).
- La page Bonjourr (affichage_bonjourr.png) est une route `/bonjourr` plein écran : fond photo flouté, crédit « Photo par Emblavoss » en bas à gauche, grande horloge HH:MM, date française (« Mardi 13 octobre »), salutation (« Bonsoir »), phrase météo en français avec température du jour et max de demain + icône jour/nuit, engrenage de réglages en bas à droite. Le bouton « ← Accueil » en haut à gauche est déjà fourni par App.vue pour toute route non-home.
- Météo : Open-Meteo (sans clé API, fiable) plutôt que l'API privée api.bonjourr.fr ; géolocalisation navigateur avec repli Paris ; repli silencieux (bloc masqué) si le réseau échoue — les tests unitaires tournent sur fixtures, jamais sur le réseau.
- Fond : image locale dans public/bonjourr/ (le crédit « Photo par Emblavoss » est conservé tel quel d'après la capture) ; le rendu est flouté en CSS comme sur la capture.
- Vérifications : le projet n'avait AUCUN test runner → j'ajoute vitest + @vue/test-utils + happy-dom (choix minimal et idiomatique Vite). Chaque test est écrit et exécuté une fois pour voir le ROUGE avant l'implémentation.

## Case 16 (terminée le 16/10/2026) — arbitrages rendus à l'exécution

- Écart le plus lourd de la case : l'original confie la note à la librairie tierce **PocketEditor** (notes.ts l.6, l.75), un éditeur WYSIWYG markdown. Le fork ne rend donc que le **sous-ensemble** utilisé par le gabarit d'origine (titres `#`..`######`, listes `- `, cases `[ ]`/`[x]`, liens `[t](u)`, gras `**`, italique `*`), après **échappement HTML** systématique et filtrage des schémas d'URL (`http(s):`, `mailto:` seulement) : `<img src=x onerror=...>` reste du texte. C'est ce que prouve le test dédié, pas une parité de rendu avec PocketEditor.
- Édition directe sur la page : `#pocket-editor` est un `contenteditable` permanent ; le rendu markdown est affiché tant que le champ n'a pas le focus, le texte brut réapparaît au focus (l'original ne montre que l'éditeur). Le texte est lu depuis `textContent`, donc le markdown reste la source de vérité stockée.
- L'original **débouche** l'écriture (`eventDebounce`, notes.ts l.58) ; le fork enregistre à chaque frappe. Consigné : le texte d'une note tient dans un `localStorage`, mais la persistance est ici plus brutale que chez la source.
- Le gabarit traduit n'est posé que si `notes.text` est vide : l'original ne le pose que s'il est **absent** (`init.text ?? translateNotesText()`, l.73) et ses défauts n'ont pas de clé `text` ; le fork, qui a un `text: ""` par défaut, traite vide et absent de la même façon.
- Langue : `notesDefaultText` ne connaît que français et anglais, la langue inconnue retombant sur l'anglais comme l'original (l.105-107). Le catalogue complet (langList) arrive à la case 21 ; la règle de repli est, elle, déjà testée.
- Fond de note : la source ne stocke **qu'un hexadécimal** `notes.background` (`#fff`/`#000` + un chiffre d'alpha, shared/dom.ts l.103-111) ; la molette 0-15 et le bouton nuance n'écrivent que lui (settings.ts l.806-812), et `notes.opacity` (défaut 0.1, defaults.ts l.187) n'est jamais lu par l'UI. Le fork fait pareil : le panneau ne touche pas `opacity`, ce qui aurait inventé une seconde source de vérité.
- Classe `opaque` : blanc **strictement** au-delà de 7 (`opacityFromHex(hex) > 7`, notes.ts l.97) — un fond `#000f`, même très opaque, ne la prend jamais. Le seuil est testé des deux côtés parce qu'une mutation `>= 7` n'a fait échouer que cette vérification-là.
- `--notes-width` n'est posée **que si** `width` existe (l.90-92), `--notes-background` est toujours posée avec repli `#fff2` (l.95-100) : asymétrie volontaire de la source, reprise telle quelle.
- Le fork n'a pas d'équivalent au bouton « Notes shade » en icône (settings.html l.1362-1374) : une select « Nuance / Claire-Sombre » rend le même état, et l'état courant est relu sur l'hexadécimal stocké (`includes("#000")`, exactement ce que fait settings.ts l.279).
